# Отчёт S-65 — PvP UI и workflow жалоб

**Дата:** 2026-11-03 · **Этап:** E-23 Продуктовая полнота · **Статус:** ✅

## 1. Что сделано

### Backend

- Миграция `0029_pvp_complaint_review`: `pvp_complaints` + `reviewed_by`
  (FK users SET NULL), `reviewed_at`, `note`.
- `PATCH /admin/pvp/complaints/{id}` (teacher/admin): статус-машина
  open → reviewed|rejected (иначе 409/422), note до 2000 символов,
  reviewer = автор PATCH; событие аудита `pvp.complaint.review`.
- `GET /admin/pvp/complaints` расширен с ADMIN/AUDITOR до teacher/admin
  (чек-лист «очередь жалоб у admin/teacher»); DTO `ComplaintOut` дополнен
  note/reviewedBy/reviewedAt.
- `GET /pvp/rooms/mine` — активная комната пользователя (waiting/ready/
  running) для «возврата на страницу» в UI (404 — если нет).

### Frontend

- **`/pvp`** (PvpPage): выбор бота (rated-флаг), создание комнаты,
  **quick-match**, вход по коду, статус-карточка с поллингом (waiting →
  ready → running → done/cancelled/failed), отмена/старт для host,
  SSE-строка прогресса матча, финальный **replay с шахматной доской**
  (react-chessboard, шаги по полуходам «◀/▶»), **PvP-лидерборд**,
  отправка жалобы участником (ветвление по участию в комнате).
- **`/complaints`** (ComplaintsPage, teacher/admin): очередь жалоб с
  фильтром статуса, карточка причины, поле вердикта, кнопки
  «подтверждено (reviewed)» / «отклонено (rejected)».
- Навигация: `/pvp` «PvP», `/complaints` «Жалобы»; CSS `.pvp-*`.

### e2e (DoD «два браузера»)

`frontend/e2e/pvp.spec.ts` — два контекста (seed-аккаунты student1 /
student2 + admin):
- host создаёт комнату (API), гость входит **по коду из UI**;
- обе страницы поллингом ждут ready → host стартует матч →
  done на **реальном SF-воркере** (~40 ходов, result draw);
- обе страницы видят **реплей с доской**; шаг назад работает;
- жалоба host'а через UI; **контекст админа закрывает её в UI**
  (фильтр «все статусы» → note → «подтверждено») —
  **1 passed (14.1 с)** на изолированном e2e-стенде
  `scripts/e2e-targeted.ps1` (новый отладочный прогон подмножества
  спецификаций с segment reset).

## 3. Что не сделано / блокеры

- **Проверка на CI** — финальный полный e2e (`ci.yml` job e2e) после push;
  локальный прогон дал 1 passed для pvp-спеки, полный набор — со
  смешанными результатами локальной флективности (journey serial-спека
  в первую попытку) — см. риски.
- Зритель: прямого «обозревателя без участия» в UI нет (replay после
  done доступен любому — это и есть наблюдение); live-dose viewer — v0.5.

## 4. Отклонения от Design (нужны ADR?)

- Нет ADR. Статус-машина жалоб (single-переход) — из паттерна
  anticheat_flags; SSE-доска реализована через существующий
  турнирный канал (S-48) — без новых механик.

## 5. Новые факты → Design (обязаны вернуться в Design?)

- `GET /pvp/rooms/mine` — новый контракт возврата активной комнаты
  (SPEC §3.22).
- `replay?match_id=` — параметр в **snake_case** (FastAPI query), не
  camelCase: это единственный GET-параметр домена с snake-именем;
  потенциальный футчуровский дрейф — рассмотреть Cameler-нормализацию
  query в целом (S-69).
- Статус-потенциал race notes: `pvp_complaints.status` CHECK
  (open/reviewed/rejected) против partial-порядка.

## 6. Риски

- Serial-journey Playwright: полный набор периодически вспоминает
  retried-прогон (описан в S-55/S-56 fluff): attempt 1 может падать,
  attempt 2 (retry) проходит; риск — для CI-времени, не для качества.
- Открытые `pvp_complaint` хранятся бессрочно; оцениваться будут
  только active rooms (S-69/production).
