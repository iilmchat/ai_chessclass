## 1. Что сделано

- **Миграция `backend/migrations/versions/0031_s72_rls_isolation.py`**
  (`0031_s72_rls_isolation`, down_revision `0030_s67_lms_oauth`):
  - `ENABLE ROW LEVEL SECURITY` + `FORCE ROW LEVEL SECURITY` для
    `bot_stats`, `cognitive_skill_events`, `anticheat_flags`;
  - политика `s72_<table>_tenant` (`FOR ALL`, одинаковые `USING` и
    `WITH CHECK`) разрешает строку, если:
    - `current_setting('app.current_user_role', true) = 'admin'` — доступ ко
      всем строкам;
    - `user_id = current_setting('app.current_user_id', true)::bigint` — своя

    `class_members`/`classes`, без добавления денормализованного `class_id`;

    `POSTGRES_USER` в docker/CI — суперпользователь, а суперпользователи
    обходят RLS даже при `FORCE ROW LEVEL SECURITY`.

  - SQLAlchemy-событие `after_begin` на каждой транзакции выполняет
    `SET LOCAL ROLE chess_app` и транзакционно-локальный эквивалент

## 4. Отклонения от Design (нужен ADR?)

- **`class_id` не добавлялся.** ADR-015 в первой редакции предполагал
  денормализацию `class_id` и `app.current_class_id`; контракт S-72 явно
  требует проверку через `user_id` и `class_members`. Реализовано по
  контракту, ADR-015 в `Design.md` обновлён. Новый ADR не нужен.
- **Добавлена роль `chess_app` + `SET LOCAL ROLE`.** Без этого RLS не
  работал бы: docker/CI подключаются пользователем-суперпользователем,
  который обходит политики. Это техническая деталь ADR-015, отдельный ADR
  не требуется.
- **Своя строка (`user_id = current_user_id`) разрешена дополнительно к
  teacher/admin.** Иначе ломаются ученические `/skills/me` и `/bots/stats`;
  это сужение, а не расширение cross-tenant доступа.
- **Индексы на `class_id` не добавлялись**: колонки `class_id` в трёх
  таблицах нет. Проверку покрывают существующие индексы
  `ix_anticheat_flags_user`, `ix_cognitive_events_user_skill`,
  PK `bot_stats(user_id)`, `ix_class_members_user`, `ix_classes_teacher`.
- **Тестовая гигиена:** очистка `py_assignments` расширена на `e2e-%`,
  чтобы повторные прогоны не переполняли первую страницу. На архитектуру
  не влияет.

## 6. Риски

- **Производительность RLS.** Политика содержит `EXISTS`-подзапрос на
  каждую строку; индексы `class_members(user_id)` и
  `classes(teacher_id)` покрывают join, но на очень больших классах нужен
  `EXPLAIN ANALYZE` и, возможно, кэш состава класса/материализованное
  членство. В S-72 бенчмарк не снимался.
- **Утечка контекста в пуле.** Закрыта транзакционно-локальными
  настройками и повторной установкой в `after_begin`; риск остаётся только
  для кода, который выполняет SQL вне ORM-сессии или делает `RESET ROLE`.
  Полное устранение — отдельный login-пользователь БД без права `SET ROLE`.
- **JWT-роль устаревает.** Роль для RLS берётся из подписанного JWT (TTL
  15 мин); понижённый admin сохраняет RLS-обход до истечения токена.
  RBAC-проверки при этом используют роль из БД. Кандидат на ревокацию
  токенов/короткий TTL.
- **Fail-closed по умолчанию.** Сессия без контекста видит 0 строк
  RLS-таблиц; новая фоновая задача, забывшая `db_context`, не утечёт данные,
  но может молча вернуть пустой результат. Нужен code review фоновых
  путей.
- **Семантика `auditor` и лидерборда.** Глобального обхода для `auditor`
  нет: политика даёт ему только свои/teacher-строки, если он не admin.
  Публичный лидерборд ботов под контекстом ученика теперь ограничен
  доступными строками. Если продукт требует глобальное чтение — нужна
  отдельная `FOR SELECT`-политика для `auditor` и/или system-контекст для
  агрегатов.
- **Создание роли в миграции.** `CREATE ROLE` требует прав суперпользователя
  или `CREATEROLE`; в managed-PostgreSQL роль/гранты могут выдаваться
  отдельно. При отсутствии роли приложение падает fail-closed — порядок
  «миграции → API/worker» обязателен.
- **Широкие DML-гранты `chess_app`.** Роль получает DML на все таблицы
  `public` (приложению нужны и не-RLS таблицы). Это не расширяет RLS, но
  при компрометации SQL-пути ограничивает ущерб только DML, без DDL.
