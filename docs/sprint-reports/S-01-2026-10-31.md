## 1. Что сделано

- Инфраструктура: `docker-compose.dev.yml` — `chessclass-db`
  (pgvector/pgvector:pg17, :5438), `chessclass-redis` (:6384), `chessclass-api`

  `.env.example` (контракт Design §15.2), `.env` — копия для dev.
- Git: репозиторий инициализирован, ветка `main`.

## 5. Новые факты → Design (обязаны вернуться в Design?)

- volumes получили явные имена `chessclass_pgdata`/`chessclass_redisdata`
  (иначе compose создал бы `chessclass_chessclass_*`) — соответствует
  контракту Design §15.1/KI-001, правка Design не нужна (имена совпадают).
- Единый тег образа `chessclass/backend:dev` для api/worker/migrate —
  деталь реализации compose, в Design не дублируется.

## 6. Риски

- `npm install` в `chessclass-web` выполняется при каждом старте контейнера
  (node_modules в bind-монтированной папке, Windows-хост). Приемлемо для dev;
  если станет медленно — печь node_modules в образ (решение в E-10 или по факту).
- `--reload` uvicorn на bind-монтировании Windows тоже может подтормаживать
  на больших объёмах кода; контролируем по факту.
- Секреты dev (`JWT_SECRET=change-me-dev-s01`) — только для локальной разработки.
