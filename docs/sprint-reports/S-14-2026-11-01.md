# Отчёт S-14 — Ассистент E2E (сквозной сценарий D)

**Дата:** 2026-11-01 · **Этап:** E-05 RAG и сквозной ассистент · **Статус:** ✅ (этап завершён)

## 1. Что сделано

- **Knowledge-блок** в prompt_builder (§8.6): `build_messages(..., knowledge=[])`
  — RAG-чанки вставляются перед фактами («факты менять нельзя» ниже knowledge).
- `python_teacher`: hint и comment собирают RAG-контекст по теме задания
  (топ-2, домены python/general, `k=2`); сбой retrieval — warning + пустой
  knowledge (ассистент работает без базы знаний).
- Сквозные тесты сценариев (Design §3.4):
  - **A** сдача → вердикт + комментарий → запись `llm_calls`
    (`python_teacher.comment`);
  - **B** позиция → факты SF + объяснение → `llm_calls`
    (`chess_lab.insight`, dev — status `echo`);
  - **D** инжест знания → hint с блоком «Полезный материал (база знаний)»
    доходит до LLM (echo повторяет промпт — проверяем наличие блока).
- Фикстура `worker_role` перенесена в conftest (общая для engine/e2e).

## 2. DoD

  строка в llm_calls с route/model_used/status)

## 3. Что не сделано / блокеры

- Insight без knowledge-блока (осмысленный RAG-запрос для шахматной позиции
  требует «темы» — завяжется на PGN-метаданные/ECO в S-15+).
- Реальный LLM-провайдер (echo-режим) — контракты проверены; ключ RouterAI
  закроет последний риск R-01/§18.2.

## 4. Отклонения от Design (нужны ADR?)

- Нет ADR. Порядок блоков в промпте: request → knowledge → facts (факты
  ближе к концу — модели труднее их «переписать»); зафиксировано в SPEC §3.8.

## 5. Новые факты → Design (обязаны вернуться в Design?)

- Сбой RAG → деградация без знания, не сбой (продумано заранее §8.6
  «база знаний опциональна») — подтверждено тестом.

## 6. Риски

- Топ-2 knowledge на промпт — фикс; при росте базы знаний пересчитать
  k и порог similarity (минимум 0.1), иначе шум в промптах.
- echo-прогон scenarios в dev показывает промпт как текст ответа — удобно
  для отладки, но в прод echo отключается на уровне fallback-цепочки.
