## 3. Что не сделано / блокеры

- **Фактический push/pull GHCR не выполнен локально**: нет доступа к
  GitHub Actions/registry из этой среды. Workflow, prod-compose и локальные
  образы проверены; публикация произойдёт при push в `main` (job `publish`),
  после чего проверить `docker pull ghcr.io/iilmchat/chessclass-backend:<tag>`.
- **Реальный Sentry DSN не проверен**: в репозитории нет боевого DSN. Проверены
  старт с пустым DSN (no-op) и с фиктивным DSN (init не ломает приложение);
  фактическая доставка события — при развёртывании с боевым DSN.
- **Frontend Sentry** включается только при build-arg `VITE_SENTRY_DSN`;
  в локальной сборке без DSN код tree-shaken (Sentry выключен). Проверка
  реального события — после настройки секрета в GitHub.
- **Multiprocess-метрики** проверены на 2 воркерах; прод использует 4
  (`API_WORKERS=4`) — конфигурация та же, отдельный прогон на 4 не делался.
- **GHCR-образы для `web`** собираются из frontend Dockerfile; фактический
  `docker pull` и запуск prod-стека — на сервере/в CI.

## 4. Отклонения от Design (нужен ADR?)

- **Sentry Python SDK 2.74:** `send_default_pii` deprecated, поэтому PII
  отключён через `data_collection` (user_info/cookies/headers/query/bodies/
  gen_ai/db/queues = off). Это эквивалент прежнего `send_default_pii=False`,
  но future-proof; отдельный ADR не нужен.
- **Prod-образы жёстко указывают owner `iilmchat`**, а workflow публикует в
  `github.repository_owner`. Для форка нужно поменять owner в compose;
  вынесение в `GHCR_OWNER` — возможное улучшение, но не требуется сейчас.
- **`publish` тегирует `<sha>` + `<ref>`** (`main`/`vX.Y.Z`), а не отдельный
  `env.IMAGE_TAG` из версии. Для prod использовать релизный тег; `main`
  оставлен для staging/ручных проверок.
- **Multiprocess только для HTTP RED-метрик.** DB/Redis/outbox/retention
  gauges остаются process-local, но отражают общее состояние БД; дублирования
  бизнес-счётчиков нет. ADR не нужен, зафиксировано в runbook §16.
- **Frontend Sentry** инициализируется в `main.tsx`, а не `App.tsx` — раньше
  точка входа, ошибки рендера/импорта тоже попадают. Функционально то же.
- Новый ADR не требуется: S-92 — инфраструктурный слой.

## 6. Риски

- **Sentry и PII.** Несмотря на `data_collection=off`, интеграции/ручные
  `capture_exception` могут добавить контекст; email/токены не класть в
  `extra`/`tags`. DSN хранить только в секретах, при утечке — перевыпуск.
- **Multiprocess tmpfs.** Каталог `/tmp` эфемерный: при рестарте контейнера
  счётчики начинаются с нуля (Prometheus `rate` переживает reset). Не
  монтировать один каталог между разными контейнерами; следить за writable
  и версией `prometheus-client`.
- **GHCR-доступ и rollback.** Приватные пакеты требуют токен `read:packages`
  на сервере; rollback образом не откатывает forward-only миграции. Тег
  `main` подвижен — prod фиксировать релизным тегом.
- **Log rotation.** Docker json-file ограничивает только stdout контейнеров;
  файловые логи вне Docker без logrotate могут забить диск. `copytruncate`
  имеет окно потери строк при ротации.
- **Sentry frontend bundle.** При заданном DSN бандл/размер растут; DSN
  build-time, смена требует пересборки frontend-образа.
- **Дублирование publish/images.** `images` job собирает образы для PR,
  `publish` — для push; это осознанное дублирование (gate + registry), но
  увеличивает CI-время.
- **GHCR owner hardcode.** Форк/смена owner требует правки compose; иначе
  `pull` уйдёт в чужой namespace.
- **Секреты в build-args.** `VITE_SENTRY_DSN` не секрет в классическом смысле
  (публичный DSN), но не выводить его в логи сборки; GitHub secrets
  маскируются.
