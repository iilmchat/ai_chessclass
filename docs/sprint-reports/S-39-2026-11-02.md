# Отчёт S-39 — INSIGHT knowledge для шахмат

**Дата:** 2026-11-02 · **Этап:** E-14 · **Ветка:** main (автономный режим)

## 1. Что сделано

- **База знаний (domain=chess).** В `db/seeds_rag.py` добавлены 10
  курируемых документов: дебют, миттельшпиль, эндшпиль, безопасность
  короля, пешечная структура, расчёт вариантов, профилактика зевков,
  оценка позиции, тактика (связки/вилки), атака на короля. Всего
  chess-документов — 13 (3 были в v0.1). Seed идемпотентен по title.
- **`rag/chess.py`.**
  - `detect_phase(fen)` — opening/middlegame/endgame по числу фигур,
    материалу и номеру хода.
  - `build_chess_query(fen, topic)` — русскоязычный запрос: фаза, план,
    оценка, термины фазы, тема (blunder), шах/мат.
  - `search_chess_text` — vector/hash-поиск + лексический rerank
    (стемминг, title/phase boost) по всем chess-документам.
  - `search_chess_knowledge` — FEN-обёртка; ошибка RAG логируется и не
    ломает insight (возвращается пустой knowledge-блок).
- **Insight/blunder.**
  - `chess_lab.insight`: top-3 знания передаются в
    `build_messages(..., knowledge=...)`, возвращаются в `knowledge[]` и
    сохраняются в meta `chess_positions`.
  - `chess_lab.blunder`: знания по FEN до зевка + тема «блюндер зевок
    проверка угроз»; `knowledge[]` в ответе.
  - API: `InsightOut.knowledge`, `BlunderExplainOut.knowledge`.
  - UI ChessPage: блок «Полезные знания» для инсайта и объяснения
    блюндера; DTO обновлены.
- **Embeddings.** `LLM_EMBED_MODEL` теперь пуст по умолчанию → hash-фолбэк
  без сетевых вызовов; `.env.example`/`.env.prod.example` обновлены
  (prod задаёт 768-мерную модель явно).
- **Eval.** `scripts/chess_rag_eval.py`: 10 текстовых запросов + 3
  FEN-фазы; top-1 title проверяется по ожидаемой теме.

## 3. Что не сделано / блокеры

- **Реальные книги/статьи** не загружались: используются курируемые
  seed-документы (короткие конспекты), чтобы не нарушать авторские права
  и не тащить большие PDF в репозиторий. Формат ingest готов для
  `POST /admin/rag/ingest`.
- **Админ-просмотр eval** отдельным UI не делался: используется
  существующий `GET /admin/rag/search` и CLI-eval; для v0.2 достаточно.
- **Семантическое качество на реальной embedding-модели** не проверено:
  в dev используется hash-фолбэк; prod должен задать 768-мерную модель и
  прогнать eval повторно.
- **FEN-метаданные партий** (дебют/фаза в БД) не добавлялись: фаза
  вычисляется на лету; это осознанно, чтобы не менять схему.

## 4. Отклонения от Design

- Вместо «10 позиций» eval включает 10 текстовых запросов + 3 FEN-фазы
  (13 проверок) — покрывает и текстовый, и позиционный retrieval.
- Rerank лексический, а не cross-encoder: дешевле, детерминирован и
  достаточен для 13 документов; при росте базы — заменить/дополнить.
- `knowledge[]` добавлен в публичный ответ insight/blunder (Design §8.6
  говорил о блоке в промпте; SPEC фиксирует контракт).

## 6. Риски

- Hash-эмбеддинги чувствительны к морфологии; rerank со стеммингом
  компенсирует, но на сложных формулировках возможны misses.
- При росте chess-базы top-50 кандидатов может стать недостаточно —
  нужно увеличить k или добавить полнотекстовый поиск (tsv уже есть).
- RAG-запрос добавляет latency к insight/blunder; при недоступности
  провайдера — hash/пустой блок, деградация мягкая.
- Seed-документы — конспекты, а не первоисточники; глубина знаний
  ограничена. Для v0.2 достаточно, для школы — расширять редакционно.
