## 3. Что не сделано / блокеры

Блокеров нет.

Ограничения:

- **Нет автоматического retry-loop**: только ручной retry admin; повторные
  падения снова попадают в DLQ.
- **Нет UI-фильтров** по task/дате/статусу — только `status` + limit.
- **Retry не проверяет исходную причину**: если задача упала из-за
  consent/BLOCK/удалённых данных, повтор снова упадёт.
- **Retention не настраивается per-task**; 90 дней общий.
- **Нет escalation-алерта** (Pager/Telegram) на DLQ — только `/ops` и
  `/metrics`.

## 4. Отклонения от Design (нужен ADR?)

- **Retry — ручной admin-action**, а не автоматический: ADR-016 требовал
  аудит/повтор; ручной вариант безопаснее для side-effect задач.
- **Статус `retried`** используется как отметка без удаления строки; это
  соответствует check-constraint `failed_jobs`.
- **Правильная очередь** выбирается только для `run_match`; для остальных
  default queue достаточна, так как per-queue воркеры есть только у матчей.
- Новый ADR не нужен.

## 6. Риски

- **Дубли side effects**: retry уже выполнявшейся задачи может повторно
  списать LLM/создать отчёт; для таких задач нужен idempotency-ключ
  (S-73 частично покрывает run_match/analyze_game).
- **Очередь `run_match`**: при неизвестном opponent retry идёт в default
  queue; задача завершится ошибкой и снова попадёт в DLQ.
- **Рост DLQ**: retention 90 дней может быть большим при инциденте; нужен
  alert escalation и, возможно, 30 дней для failed_jobs.
- **Trace/consent**: retry использует старые args/trace_id; если consent
  отозван, задача снова упадёт (это ожидаемо fail-closed).
- **Audit PII**: `args` сохраняются в DLQ; для новых задач нужно следить,
  чтобы там не было кода/секретов (S-73 уже отмечал).
