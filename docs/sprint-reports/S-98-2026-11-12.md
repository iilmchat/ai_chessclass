## 4. Отклонения от Design (нужен ADR?)

- **Body scrub и metadata delete — две политики** (`email_outbox_body` и
  `email_outbox`), чтобы в `/admin/observability/retention/status` видеть
  раздельно PII-очистку и удаление; `RetentionResult.scrubbed` расширяет
  контракт без ломающих изменений.
- **DSAR дополнительно обезличивает профиль, `parental_consents.parent_email`
  и `telegram_outbox`** сверх перечисленного минимума — это тот же PII;
  audit/llm/legal_holds не трогаются, как требует Design.
- **Legal hold в retention применён к `email_outbox`** (там PII и основной
  риск); DSAR блокируется для всех данных субъекта. ADR не нужен.

## 6. Риски

- **Legal hold можно забыть отозвать** — DSAR/retention будут блокироваться;
  алерт `ChessClassLegalHoldActive` (info) напоминает, ревизия — по
  `expires_at`/audit_logs.
- **DSAR и FK-связи.** Удаление review/pvp/telegram рассчитано на
  `ON DELETE CASCADE`; новые таблицы с `user_id` нужно добавлять в erase,
  иначе останется PII. Тест покрывает ключевые таблицы.
- **Retention body только `sent/failed`.** `pending` не чистится, чтобы не
  потерять письмо; parked failed после 90 дней удаляется, но `body`
  очищается раньше.
- **Архив метаданных.** `body` исключён, но `recipient` остаётся в архиве
  (метаданные для аудита); доступ к `RETENTION_ARCHIVE_DIR` ограничить.
- **Audit_logs содержат actor_email.** По требованию они сохраняются; при
  DSAR email субъекта в старых audit-строках не переписывается (аудит).
- **Legal hold subject_id — строка.** Для user API ожидает числовой id в
  строке; ошибка типа приведёт к «не найден»/409 без утечки данных.
