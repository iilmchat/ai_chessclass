## 3. Что не сделано / блокеры

Блокеров нет.

Ограничения релиза:

- **SMTP для parental consent в prod** не подключён: dev возвращает
  ссылку/пишет `[dev-email]`; для prod нужен SMTP-транспорт (как для
  verify-email).
- **Жёсткое enforcement согласия** на все учебные функции не включено:
  workflow, статус, аудит и UI готовы; школы/оператор могут требовать
  `granted` до начала занятий. Автоматический блок LLM/отчётов для
  child/teen без согласия — кандидат v0.6.
- **Юридическая проверка** privacy-policy/incident-response: контакты и
  реквизиты — шаблонные (`privacy@`/`security@chessclass.dev`), перед
  публичным запуском согласовать с юристом/DPO.
- `failed_jobs` retention/ручной retry, OTel Collector, live TTS, live LRS
  и a11y react-chessboard остаются в backlog (см. §7).

## 6. Риски

- **Возраст декларируется пользователем.** Ребёнок может указать `adult`
  и обойти запрос согласия; школа должна проверять возраст/согласие
  организационно. Технически можно добавить подтверждение учителем.
- **Владение email родителя не верифицируется отдельно** — согласие
  подтверждается possession of token из письма; ссылка одноразовая,
  TTL 7 дней, но в dev токен возвращается клиенту для удобства.
- **SMTP в prod отсутствует** — без него запросы согласия не доходят до
  родителей; это блокер эксплуатации, не кода.
- **Consent не блокирует учебные LLM/отчёты автоматически.** До v0.6
  школа должна не начинать обработку child/teen без `granted`.
- **Privacy/incident документы — шаблон.** Контакты, реквизиты, сроки и
  обязанности уведомления нужно проверить юридически; для разных юрисдикций
  (РФ/ЕС/США) требования различаются.
- **Retention consent/failed_jobs** не автоматизирован; история согласий
  хранится для доказуемости, DLQ растёт до появления retention.
- **Данные уходят субпроцессорам** (LLM/Telegram/LRS) — политика это
  описывает, но школа должна заключить договоры и настроить allowlist.
