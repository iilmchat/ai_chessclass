## 1. Что сделано

  получает `deploy/seccomp-sandbox.json`. Отдельный sandbox-контейнер

## 3. Что не сделано / блокеры

- Отдельный контейнер `network_mode: none` не развёрнут: выбран bwrap как
  менее инвазивный путь; UDS-вариант остаётся альтернативой для v0.9+.
- В окружениях без user namespaces или без seccomp-профиля bwrap не
  создаст namespace; executor делает fallback (`unshare` при root/plain) с
  `network_isolation_enforced=false` и warning. Это ограничение
  зафиксировано в runbook §19.
- Боевой prod-стенд не проверялся; локальный Docker-контур и e2e зелёные.

## 4. Отклонения от Design (нужен ADR?)

- **Путь А вместо отдельного контейнера** из TODO: bwrap проверен без
  `--privileged`; отдельный контейнер сложнее и не даёт выигрыша при
  работающем bwrap. ADR не нужен: это выбор механизма в рамках S-97.
- **Добавлен seccomp-профиль.** Docker default блокирует namespace/mount
  syscalls для non-root; `seccomp=unconfined` был бы хуже. Профиль —
  default + минимальный набор syscalls, без CAP_SYS_ADMIN.
- **Fallback на `unshare`/none** сохранён для несовместимых ядер; это
  осознанная деградация с явным warning, а не тихий обход.

## 6. Риски

- **bwrap и ядро.** В части ядер/дистрибутивов unprivileged user namespaces
  выключены (`kernel.unprivileged_userns_clone=0` или AppArmor-ограничение);
  тогда fallback снижает гарантию до `unshare`/none с warning.
- **Seccomp-профиль.** Копия Docker default может отставать при обновлении
  Docker/ядра; при новых syscalls возможны отказы. Профиль нужно
  пересматривать при обновлении runtime; не заменять на `unconfined`.
- **Fallback = weaker isolation.** Если bwrap сломан, сеть может остаться
  доступной; мониторить `network_isolation_enforced=false` и warning.
- **Latency/overhead.** bwrap добавляет fork/namespace/mount на каждый
  запуск; для учебных заданий приемлемо, для массовых матчей — следить за
  p95.
- **`/proc`/`/dev` внутри bwrap.** Минимальные, но не пустые; при
  расширении sandbox пересмотреть binds (не монтировать хост-каталоги).
