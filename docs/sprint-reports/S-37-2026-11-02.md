# Отчёт S-37 — Concurrency матчей и справедливость

**Дата:** 2026-11-02 · **Этап:** E-13 · **Ветка:** main (автономный режим)

## 1. Что сделано

- **Per-queue лимиты.** `domains/bot_lab/queues.py`:
  - `arq:matches:random` — 2 слота;
  - `arq:matches:greedy` — 1;
  - `arq:matches:minimax` — 1;
  - `arq:matches:sf` — 1 (все stockfish-*).
  Суммарно 5 матчей; каждая очередь обслуживается отдельным arq-воркером,
  поэтому тяжёлая SF-очередь не блокирует random/greedy/minimax.
- **Лимит на пользователя.** API считает pending/running матчи за последние
  10 минут; 6-й активный матч → **429 `match_limit`**, счётчик отказов
  инкрементируется в Redis (`matchq:refused:{kind}`).
- **Enqueue.** `POST /bots/{id}/match/run` ставит job в очередь своего
  соперника (`_queue_name`); worker читает `WORKER_QUEUE`/`WORKER_MAX_JOBS`.
- **Compose.** dev/e2e/prod поднимают 4 match-воркера; default `worker`
  остаётся на analyze/pdf.
- **Метрики.** `GET /api/v1/admin/matches/metrics?hours=24`:
  `total`, `byOpponent`, `timeouts`, `avgDurationMs`, `p95DurationMs`,
  `refused`, `queues[{kind,queue,limit,queued,active,refused}]`.
  Active-счётчики — Redis-set с TTL; очереди — `ZCARD` arq.
- **Нагрузочный smoke.** `backend/scripts/match_load.py`: 2 random + greedy +
  minimax2 + stockfish-1400, 5/5 finished.

## 3. Что не сделано / блокеры

- **Строгий round-robin внутри очередей** не реализован: очереди
  изолированы per-kind, внутри — FIFO. Это устраняет голодание между
  типами соперников; round-robin между пользователями внутри одной
  очереди — возможная следующая оптимизация.
- Pending-матч при падении worker'а остаётся в БД до 10-минутного окна
  и временно занимает слот лимита; отдельная очистка/перевод в failed —
  кандидат в S-38/S-39.
- Метрики active/refused — Redis; при рестарте Redis счётчики теряются
  (для длительной истории — БД/метрики S-38).

## 4. Отклонения от Design

- «Round-robin по id очередей» реализован как **per-queue workers**
  (каждая очередь получает гарантированный слот), а не общий scheduler.
  Это даёт отсутствие starvation и проще в эксплуатации; FIFO остаётся
  внутри очереди. Design §7.2/§12.3/§15.1 обновлены.
- Match-воркеры — отдельные контейнеры; суммарная concurrency 5.

## 5. Новые факты → Design / SPEC

- Очереди `arq:matches:{random,greedy,minimax,sf}`, лимиты 2/1/1/1.
- `POST /bots/{id}/match/run` → 202 или 429 `match_limit`.
- `GET /admin/matches/metrics` — контракт в SPEC §3.10.
- `WORKER_QUEUE`/`WORKER_MAX_JOBS` — env-контракт воркера.
- `scripts/match_load.py` — канонический нагрузочный smoke.

## 6. Риски

- 4 дополнительных match-воркера увеличивают число контейнеров/CPU;
  в prod это осознанный обмен latency на изоляцию очередей.
- Redis active-set с TTL 10 мин; при зависшем матче возможен временный
  «фантомный» active-слот до истечения TTL.
- Random-очередь с 2 слотами может занять оба слота одним пользователем
  (лимит 5 общий); fairness между пользователями внутри очереди — backlog.
